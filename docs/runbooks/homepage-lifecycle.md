# Homepage — Lifecycle Runbook

## 1. Purpose

This runbook describes the operational procedures required to manage the Homepage service in the PersonalCloud local development environment.

It covers:

- Service startup and shutdown.
- Restart and status verification.
- Application access and log inspection.
- Container removal and recreation.
- Application update and rollback procedures.
- Basic troubleshooting.

These procedures must be performed from the Homepage Docker Compose directory.

**Project directory:**

`~/projects/PersonalCloud/compose/homepage`

## 2. Prerequisites

Before executing any operational procedure, verify that:

- Ubuntu WSL2 is running.
- Docker Desktop is running.
- Docker Engine is accessible from Ubuntu.
- The active Docker context is `default`.
- The Homepage `compose.yaml` file is available.
- The operator has access to the PersonalCloud project directory.

Navigate to the Homepage directory:

```bash
cd ~/projects/PersonalCloud/compose/homepage
```

Verify Docker Engine connectivity:

```bash
docker info --format 'Server={{.ServerVersion}} | OS={{.OperatingSystem}}'
```

The command must return Docker Engine information without connection errors.

## 3. Service Startup

### 3.1 Start Homepage

Execute:

```bash
docker compose up -d
```

This command creates the required container and network when they do not exist and starts the application in detached mode.

The `-d` option allows the service to continue running in the background without attaching the terminal to its output.

### 3.2 Verify Service Status

Execute:

```bash
docker compose ps
```

The Homepage container must appear with a running status.

The expected status is:

`Up (healthy)`

### 3.3 Verify Application Access

Open the following address in a browser:

`http://127.0.0.1:3000`

Verify that the PersonalCloud dashboard loads successfully.

## 4. Service Shutdown

To stop Homepage without removing its container, execute:

```bash
docker compose stop homepage
```

This operation stops the application while preserving:

- The existing container.
- Its configuration.
- The Compose network.
- The locally stored image.
- The bind-mounted configuration files.

Verify the container status:

```bash
docker compose ps -a
```

The container should appear with an exited status.

Homepage will no longer be accessible through the browser.

## 5. Service Startup After Shutdown

To start an existing stopped container, execute:

```bash
docker compose start homepage
```

This command starts the previously created container without creating a new one.

Verify its status:

```bash
docker compose ps
```

Then access:

`http://127.0.0.1:3000`

**Important:** `docker compose start` cannot recreate a container that has already been removed. Use `docker compose up -d` when the container does not exist.

## 6. Service Restart

To restart Homepage, execute:

```bash
docker compose restart homepage
```

This operation stops and starts the existing container.

It does not recreate the container or apply changes made to the Compose configuration.

After restarting, verify the container status:

```bash
docker compose ps
```

Check the application logs if necessary:

```bash
docker compose logs --tail=50 homepage
```

## 7. Log Management

### 7.1 Display Recent Container Logs

Execute:

```bash
docker compose logs --tail=50 homepage
```

This displays the latest 50 log lines generated by the container.

### 7.2 Follow Container Logs in Real Time

Execute:

```bash
docker compose logs -f homepage
```

The `-f` option follows the log output continuously.

Press `Ctrl+C` to stop displaying logs.

This does not stop the Homepage container.

### 7.3 Application Log Files

Homepage also maintains application log files in its persistent configuration directory:

`config/logs/`

These files are stored outside the container through the bind mount.

## 8. Service Removal

To stop and remove the Homepage container and its Compose network, execute:

```bash
docker compose down
```

This operation removes:

- The Homepage container.
- The Compose network `homepage_default`.

It preserves:

- The Docker image.
- The host configuration directory.
- The application configuration files.
- The application logs stored in the bind-mounted directory.

**Warning:** Do not use `docker compose down -v` as a routine shutdown procedure.

The `-v` option removes named and anonymous Docker volumes associated with the Compose project. It can cause persistent data loss when those volumes contain application data.

Homepage currently uses a bind mount for its configuration, but this must not be assumed for future services.

## 9. Application Updates

Homepage uses an explicitly pinned Docker image version.

**Current image:**

`ghcr.io/gethomepage/homepage:v2.8.0`

Updates must be performed deliberately.

An actual version update and rollback have not yet been tested. The following procedure is documented for future use.

### 9.1 Pre-Update Checks

Before updating:

- Review the official Homepage release notes.
- Identify changes that may affect configuration compatibility.
- Verify that the new image supports the required architecture.
- Record the currently deployed image version.
- Create a project backup using `docs/backup/backup-and-restore.md`.
- Confirm that the backup passes its integrity checks.

Do not update to an unpinned `latest` image.

### 9.2 Update the Compose Configuration

Modify the image version in:

`compose.yaml`

Use the explicitly approved version.

Do not modify unrelated settings as part of the same change unless necessary.

### 9.3 Validate the Compose Configuration

Execute:

```bash
docker compose config --quiet
```

If the command completes successfully, the Compose configuration is valid.

Do not proceed if validation reports an error.

### 9.4 Download the Updated Image

Execute:

```bash
docker compose pull homepage
```

This downloads the image version specified in the Compose configuration without starting or recreating the container.

### 9.5 Apply the Update

Execute:

```bash
docker compose up -d
```

Docker Compose detects the image change and recreates the container when necessary.

The configuration remains outside the container through the bind mount.

### 9.6 Post-Update Validation

Execute:

```bash
docker compose ps
docker compose logs --tail=50 homepage
```

Verify:

- The container is running and healthy.
- No relevant startup errors appear in the logs.
- The dashboard is accessible.
- Existing dashboard settings, services, and bookmarks are preserved.
- The application behaves as expected.

Do not consider the update successful until these checks pass.

## 10. Application Rollback

If an update causes problems, restore the previously working image version.

For the current deployment, that version is:

`ghcr.io/gethomepage/homepage:v2.8.0`

### 10.1 Restore the Previous Image Version

Modify the image tag in `compose.yaml` to the previously working version.

### 10.2 Validate the Compose Configuration

Execute:

```bash
docker compose config --quiet
```

Confirm that the configuration is valid.

### 10.3 Retrieve the Previous Image

Execute:

```bash
docker compose pull homepage
```

This ensures the previously working image is available locally.

### 10.4 Recreate the Container

Execute:

```bash
docker compose up -d
```

Docker Compose recreates the container using the restored image version when necessary.

### 10.5 Verify Recovery

Execute:

```bash
docker compose ps
docker compose logs --tail=50 homepage
```

Verify that Homepage is running, healthy, and accessible.

A rollback does not necessarily reverse application configuration changes made by a newer version.

If the new version modified persistent configuration incompatibly, evaluate restoring the corresponding configuration backup before starting the previous version.

Do not overwrite the current configuration without first preserving it and reviewing the recovery requirements.

## 11. Troubleshooting

### 11.1 Docker Engine Is Unavailable

Symptoms:

- Docker commands return connection errors.
- The Docker daemon cannot be reached.

Check:

```bash
docker info
```

Verify that Docker Desktop is running in Windows.

Also verify the active context:

```bash
docker context show
```

The expected context in the current Ubuntu environment is:

`default`

### 11.2 Homepage Is Not Running

Check:

```bash
docker compose ps -a
docker compose logs --tail=100 homepage
```

Inspect the container status and logs to identify startup failures.

### 11.3 Homepage Is Not Accessible

Check:

```bash
docker port homepage
```

Expected binding:

`3000/tcp -> 127.0.0.1:3000`

Verify that Docker Desktop and the container are running.

Also confirm that the browser is accessing:

`http://127.0.0.1:3000`

### 11.4 Configuration Changes Are Not Visible

Verify that the expected configuration file was saved in:

`config/`

Check the application logs for configuration errors.

If necessary, restart the container:

```bash
docker compose restart homepage
```

## 12. Operational Safety Rules

The following rules apply to Homepage administration:

- Do not publish the service on all host network interfaces without an explicit security review.
- Do not mount the Docker Engine socket inside the Homepage container.
- Do not use `docker compose down -v` as a routine lifecycle operation.
- Do not update the image without reviewing the new version and confirming that a tested backup is available.
- Preserve application configuration outside the container.
- Use explicitly pinned image versions.
- Verify service health after every significant change.
- Document relevant changes and operational incidents.

- Bind mount verification.
- Persistent configuration verification.

- Dashboard rendering.
- Service card and bookmark display.
- Date and time widget.
- DuckDuckGo search widget.
- External bookmark navigation.
- Responsive layout verification at approximately 390 pixels wide.

**Project-level backup and restoration**

- Project archive creation.
- SHA-256 verification.
- GZIP integrity verification.
- Archive content inspection.
- Extraction to a temporary directory.
- Comparison of extracted files with archive contents.
